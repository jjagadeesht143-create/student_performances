# Student Performance Analysis & Prediction System

An end-to-end data science + full-stack web application that analyzes student
academic performance and predicts a student's final score and performance
category using machine learning.

---

## 1. Problem Statement

Educational institutions collect a lot of data about students — study habits,
attendance, past scores, assignment performance — but often don't use it
proactively. This project builds a system that:

- Stores and manages student records.
- Analyzes what factors are associated with strong or weak performance.
- Predicts a student's likely final score **before** the final exam, using
  only information that would realistically be available at that point.

## 2. Objective

Build a complete, working Data Science + Flask web application that takes
pre-exam student data and predicts final academic performance, while
strictly avoiding target leakage and demonstrating sound ML methodology.

## 3. Features

- **Student Data Management** — add, edit, delete, view, and search student
  records (MySQL-backed, parameterized queries).
- **Data Analysis** — 9 charts covering score/attendance distributions,
  study time & attendance vs. score, gender comparisons, performance
  category breakdown, and a correlation heatmap.
- **Machine Learning** — a regression model predicts the numeric
  `final_score`; a classification model predicts a `performance_category`
  (Excellent / Good / Average / Needs Improvement).
- **Prediction Page + REST API** — enter a student's pre-exam data and get
  an instant, clearly-labeled model estimate.

## 5. Dataset Description

**No real-world dataset was provided for this project.** `data/raw/students.csv`
is a **synthetic dataset**, generated by `data/generate_synthetic_dataset.py`
with a fixed `random_state=42` for reproducibility (500 students after
cleaning). It is built with realistic, noisy relationships (more study time,
attendance, and stronger prior performance tend to raise the final score)
specifically so the EDA and ML pipeline have genuine signal to find — but
it is **not real student data** and must never be presented as such. To use
your own real dataset, replace `data/raw/students.csv` with the same column
schema and re-run the pipeline.

Columns: `student_id, name, age, gender, study_time, attendance,
previous_score, assignment_score, parental_education,
extracurricular_activity, final_score`.

## 6. Data Preprocessing

Handled in `src/data_preprocessing.py`:

- A **data quality report** (shape, dtypes, missing values, duplicates,
  descriptive stats) is printed *before* any cleaning happens.
- Exact duplicate rows are dropped (data-entry artifacts, safe pre-split).
- Rows with a missing target (`final_score`) are dropped — a missing label
  can't be trained or evaluated on, and imputing one would fabricate ground
  truth.
- Feature-level missing-value imputation and scaling/encoding are
  **deliberately not done at the whole-dataset level** — they live inside
  the scikit-learn pipeline, fit only on the training split, so no
  information from the test set leaks into training.

## 7. Exploratory Data Analysis

Generated by `src/eda.py`, saved to `outputs/figures/` (and mirrored into
`static/img/` for the web app): score distribution, attendance distribution,
study time vs. score, attendance vs. score, previous score vs. score,
gender-wise performance, performance category distribution, and a
correlation heatmap.

**Actual correlations found** (final_score vs. each numeric feature):
study_time 0.54, previous_score 0.37, attendance 0.26, assignment_score 0.24,
age ~0.04 (no relationship, as expected for a non-predictive column).

## 8. Machine Learning Methodology

- **Input features** (known before the final exam): `study_time`,
  `attendance`, `previous_score`, `assignment_score`, `parental_education`,
  `extracurricular_activity`.
- **Targets**: `final_score` (regression) and a `performance_category`
  derived from `final_score` *after* the train/test split (classification).
- **Leakage prevention**:
  - `train_test_split` runs before any preprocessing is fit.
  - All imputation/scaling/encoding lives inside a `Pipeline` +
    `ColumnTransformer`, fit only on `X_train`.
  - The classification target is derived independently for the train and
    test splits from their own `final_score` values.
  - `final_score`, `student_id`, and `name` are never used as features.
- **Cross-validation**: 5-fold (`KFold` for regression, `StratifiedKFold`
  for classification) on the training split only.

## 10. Evaluation Metrics (actual results from this run, `random_state=42`)

**Regression** (held-out test set, 100 students):

| Model | CV R² (train) | Test MAE | Test RMSE | Test R² |
|---|---|---|---|---|
| **Linear Regression (selected)** | 0.662 | 5.02 | 6.29 | **0.548** |
| Random Forest Regressor | 0.585 | 5.07 | 6.65 | 0.495 |

**Classification** (held-out test set, 100 students):

| Model | CV Accuracy (train) | Test Accuracy | Test Precision | Test Recall | Test F1 |
|---|---|---|---|---|---|
| **Logistic Regression (selected)** | 0.715 | 0.760 | 0.762 | 0.760 | **0.759** |
| Random Forest Classifier | 0.708 | 0.740 | 0.714 | 0.740 | 0.724 |

Confusion matrix and full per-class report: see
`outputs/evaluation_report.txt` and `outputs/figures/confusion_matrix.png`.
Model selection was based purely on these held-out test metrics — not on
arbitrary preference. Note the "Excellent" and "Needs Improvement" classes
have very few examples in this synthetic dataset, so their per-class
metrics are noisy; this is disclosed rather than hidden.

These numbers are genuine outputs of running this project's code — they
are modest, not inflated, and are not claimed to generalize to real
student populations.

## 11. API Documentation

### `POST /api/predict`

Request body (JSON):
```json
{
  "study_time": 4,
  "attendance": 85,
  "previous_score": 72,
  "assignment_score": 80,
  "parental_education": "Graduate",
  "extracurricular_activity": "Yes"
}
```

Success response (200):
```json
{
  "predicted_score": 78.5,
  "performance_category": "Good"
}
```

Error response (400) — invalid/missing fields, e.g.:
```json
{ "error": "'attendance' must be between 0 and 100." }
```

Valid values: `parental_education` ∈ {High School, Bachelors, Graduate};
`extracurricular_activity` ∈ {Yes, No}; numeric fields must be within their
realistic ranges (see `src/predict.py::validate_input`).

## 12. Database Design

MySQL database `student_performance_db` with two tables:

- **students**: id, name, age, gender, study_time, attendance,
  previous_score, assignment_score, parental_education,
  extracurricular_activity, created_at.
- **predictions**: id, student_id (FK → students.id), predicted_score,
  performance_category, model_name, created_at.

Schema: `data/schema.sql`. All queries use parameterized placeholders
(`%s`) — never string concatenation — to prevent SQL injection. Credentials
are read from environment variables (`.env`), never hardcoded (`.env.example`
provided).

## 17. Authentication and Google OAuth

The application opens at `/` with the login page. Dashboard, student,
analysis, prediction, and prediction API routes require an authenticated
session. Local accounts are stored in the `users` table with Werkzeug password
hashes. Run `data/schema.sql` against the existing database to add that table;
it does not modify student or prediction records.

Copy `.env.example` to `.env` and set `FLASK_SECRET_KEY` to a long random value.
Google sign-in is optional. To enable it, set `GOOGLE_CLIENT_ID` and
`GOOGLE_CLIENT_SECRET`, then register this exact redirect URI in Google Cloud:

`http://127.0.0.1:5000/auth/google/callback`

To configure Google OAuth locally:

1. Create or select a project in [Google Cloud Console](https://console.cloud.google.com/).
2. Configure the OAuth consent screen and add the required test users if the app is in testing mode.
3. Create an OAuth Client ID for a Web application.
4. Add the redirect URI above under Authorized redirect URIs.
5. Put the client ID and secret only in `.env`, never in templates or source control.

Password reset displays an honest configuration message until an email service
is configured; no fake reset email is sent.
